Kubernetes Security Briefing — July 30, 2026
This week: **2 critical CVEs (AKS auth bypass at CVSS 10.0, TimesTen K8s Operator RCE at CVSS 9.9), a wave of Oracle TimesTen K8s Operator vulnerabilities, and a new botnet targeting exposed AI services for K8s tokens.**

---

## 🔴 Critical

### 1. CVE-2026-56163 — Microsoft Azure Kubernetes Service Missing Authentication → Privilege Escalation
**Source:** [GitHub Advisory](<https://github.com/advisories/GHSA-2j44-cf99-2fgr>)
An unauthorized attacker can leverage missing authentication for a critical function in Microsoft Azure Kubernetes Service to elevate privileges over the network. This allows complete cluster compromise without any prior authentication.
- **CVSS:** 10.0 | **Affected:** Microsoft AKS (versions TBD) | **Fix:** Apply AKS security patch via Azure portal
- **Mitigation:** Restrict network access to AKS API server, enable Azure AD integration, review AKS audit logs for unauthorized access attempts
- **Reference:** <https://github.com/advisories/GHSA-2j44-cf99-2fgr>

### 2. CVE-2026-60402 — Oracle TimesTen In-Memory Database Kubernetes Operator RCE
**Source:** [GitHub Advisory](<https://github.com/advisories/GHSA-pr5r-gwh3-wx7x>)
A critical vulnerability in the Oracle TimesTen In-Memory Database Kubernetes Operator (version 26.1.1.1.0) allows a low-privileged attacker with network access via HTTPS to achieve complete compromise, including RCE. This can lead to full cluster-level impact via container escape.
- **CVSS:** 9.9 | **Affected:** TimesTen K8s Operator 26.1.1.1.0 | **Fix:** Upgrade to patched version (contact Oracle support)
- **Mitigation:** Restrict network access to the TimesTen Operator; apply principle of least privilege to service accounts; monitor for unusual API calls to the operator
- **Reference:** <https://github.com/advisories/GHSA-pr5r-gwh3-wx7x>

## 🟡 High

### 3. CVE-2026-16745 — Red Hat OpenShift AI odh-dashboard Authentication Bypass
**Source:** [GitHub Advisory](<https://github.com/advisories/GHSA-h5q4-fjj4-4792>)
A flaw in odh-dashboard (the web console of Red Hat OpenShift AI / RHOAI) caused by incorrect network binding allows a malicious actor within the cluster to bypass authentication and impersonate any user by providing an arbitrary access token. This leads to unauthorized data access and potential cluster-wide compromise.
- **CVSS:** 8.8 | **Affected:** Red Hat OpenShift AI (RHOAI) | **Fix:** Apply Red Hat security update
- **Mitigation:** Restrict pod-to-pod network policies; monitor for anomalous dashboard API access; apply the latest RHOAI patch
- **Reference:** <https://github.com/advisories/GHSA-h5q4-fjj4-4792>

### 4. CVE-2026-50570 — Fission CAP_SYS_TIME PodSpec Validation Bypass → Cross-Tenant Clock Corruption
**Source:** [GitHub Advisory](<https://github.com/advisories/GHSA-qf5v-m7p4-95rp>)
Fission (Kubernetes-native serverless framework) prior to v1.25.0 has an incomplete capability denylist in Environment/Function PodSpec validation. A tenant can add CAP_SYS_TIME to their function PodSpec, allowing them to corrupt wall-clock time on the node, affecting all other tenants on the same node.
- **CVSS:** 8.5 | **Affected:** Fission < 1.25.0 | **Fix:** Upgrade to Fission v1.25.0+
- **Mitigation:** Temporarily enforce PodSecurityStandards at the cluster level; deploy admission webhooks to block CAP_SYS_TIME
- **Reference:** <https://github.com/advisories/GHSA-qf5v-m7p4-95rp>

### 5. CVE-2026-17107 — RHACM cluster-proxy Service Account Impersonation Bypass
**Source:** [GitHub Advisory](<https://github.com/advisories/GHSA-vr7g-637m-v9mm>)
The service-proxy component of Red Hat Advanced Cluster Management for Kubernetes (RHACM) and multicluster-engine (MCE) appends impersonation group headers to proxied requests without first removing existing headers. A low-privileged attacker can craft requests to impersonate the service-proxy's service account and escalate to cluster admin.
- **CVSS:** 8.5 | **Affected:** RHACM / MCE cluster-proxy | **Fix:** Apply Red Hat security advisory update
- **Mitigation:** Use network policies to restrict access to the cluster-proxy endpoint; monitor for anomalous impersonation headers in audit logs
- **Reference:** <https://github.com/advisories/GHSA-vr7g-637m-v9mm>

### 6. CVE-2026-47237 — Kubeflow Authorization Token Theft
**Source:** [NVD](<https://nvd.nist.gov/vuln/detail/CVE-2026-47237>)
Kubeflow Community Distribution prior to v26.03-rc.1 is vulnerable to authorization token stealing from any user of the Kubeflow dashboard. An attacker with network access can steal tokens and gain the same permissions as the victim user, potentially accessing ML pipelines, models, and data.
- **CVSS:** 8.0 | **Affected:** Kubeflow Community Distribution < 26.03-rc.1 | **Fix:** Upgrade to 26.03-rc.1+
- **Mitigation:** Enable OIDC with short token lifetimes; restrict network access to Kubeflow dashboard; implement session revocation mechanisms
- **Reference:** <https://nvd.nist.gov/vuln/detail/CVE-2026-47237>

### 7. CVE-2026-18381 — Red Hat koku-metrics-operator SSRF to Credential Leak
**Source:** [GitHub Advisory](<https://github.com/advisories/GHSA-wfh6-5fvj-2qcg>)
The koku-metrics-operator for Red Hat OpenShift allows a user who can edit the CostManagementMetricsConfig custom resource to specify an arbitrary upload URL. The operator attaches its own Kubernetes service account token to requests made to that URL, creating an SSRF vector that leaks cloud credentials.
- **CVSS:** 7.6 | **Affected:** Red Hat OpenShift with koku-metrics-operator | **Fix:** Apply Red Hat advisory update
- **Mitigation:** Restrict who can edit CostManagementMetricsConfig CRs; use network policies to limit egress from the operator pod
- **Reference:** <https://github.com/advisories/GHSA-wfh6-5fvj-2qcg>

### 8. GHSA-6vch-q96h-7gc3 — etcd TLS Handshake Unbounded Goroutines Denial of Service
**Source:** [GitHub Advisory](<https://github.com/advisories/GHSA-6vch-q96h-7gc3>)
etcd's `tlsListener.acceptLoop` spawns unbounded TLS handshake goroutines with no deadline. An unauthenticated attacker can open numerous TLS connections, exhausting memory and CPU on etcd servers, leading to cluster unavailability.
- **CVSS:** 7.3 (CVSS:4.0) | **Affected:** etcd (all versions prior to patch) | **Fix:** Upgrade to patched etcd version
- **Mitigation:** Restrict network access to etcd ports (2379, 2380); use firewall rules to limit connection rates; deploy rate-limiting proxies in front of etcd
- **Reference:** <https://github.com/advisories/GHSA-6vch-q96h-7gc3>

### 15. CVE-2026-44210 — Kata Containers VM Escape via virtiofsd Argument Injection
**Source:** [GitHub Advisory](<https://github.com/advisories/GHSA-rr59-xxvx-96qr>)
Kata Containers prior to v3.31.0 ships with a default configuration that allows pod creators to inject arbitrary virtiofsd arguments through default-enabled pod annotations. A malicious pod can escape the VM sandbox and compromise the host with critical confidentiality, integrity, and availability impact.
- **CVSS:** 5.8 (CVSS:4.0) | **Affected:** Kata Containers < 3.31.0 | **Fix:** Upgrade to Kata Containers v3.31.0+
- **Mitigation:** Audit and restrict pod annotation permissions; disable unused annotation-based configuration
- **Reference:** <https://github.com/advisories/GHSA-rr59-xxvx-96qr>

### 16. CVE-2026-65601 — Traefik Kubernetes Gateway API Namespace Confusion
**Source:** [GitHub Advisory](<https://github.com/advisories/GHSA-6mxq-jr92-3h2r>)
Traefik 3.7.0-3.7.6 contains a namespace confusion vulnerability in the Kubernetes Gateway API provider. When resolving HTTPRoute extension filters, Traefik uses the backend Service namespace instead of the HTTPRoute's namespace, potentially allowing cross-namespace access to extension filter resources.
- **CVSS:** 5.3 (CVSS:4.0) | **Affected:** Traefik 3.7.0-3.7.6 | **Fix:** Upgrade to Traefik 3.7.7+
- **Mitigation:** Audit HTTPRoute definitions; ensure Gateway API provider uses explicit namespace restrictions
- **Reference:** <https://github.com/advisories/GHSA-6mxq-jr92-3h2r>

### 17. CVE-2026-65602 — Traefik IngressRouteTCP crossProviderNamespaces Bypass

## 🟢 Low / Informational

### 18. CVE-2026-15687 — Kubernetes Java Client Arbitrary File Write via copyDirectoryFromPod
**Source:** [GitHub Advisory](<https://github.com/advisories/GHSA-95wq-2cx3-rp73>)
A compromised pod can create files in arbitrary locations on a client machine executing `copyDirectoryFromPod` when `enableTarCompressing` is set to false. This path traversal via non-tar copy affects client machines using the Kubernetes Java client library.
- **CVSS:** 2.4 | **Affected:** Kubernetes Java client library (versions using non-tar copy) | **Fix:** Enable tar compression or use patched version
- **Mitigation:** Always use tar-compressed copy operations (`enableTarCompressing=true`) when using the K8s Java client
- **Reference:** <https://github.com/advisories/GHSA-95wq-2cx3-rp73>

### 20. NadMesh Botnet Targets Exposed AI Services for Kubernetes Tokens and Cloud Keys
**Source:** [The Hacker News](<https://thehackernews.com/2026/07/new-nadmesh-botnet-hunts-exposed-ai.html>)
XLab researchers discovered the NadMesh botnet actively scanning the internet for exposed AI services (including MCP endpoints and model deployments). Once inside, it exfiltrates cloud keys from environment variables, Kubernetes service account tokens, `~/.aws/config`, `.env`, and `~/.docker/config.json`. The botnet uses Docker API RCE (30.31% of traffic) and Jenkins exploits to gain initial access. Over 17,700 deployments have been compromised.
- **Affected:** Exposed K8s API servers, Docker daemons, AI/MCP services with weak or no auth
- **Mitigation:** Never expose K8s API server or Docker socket to the public internet; use network policies; rotate all credentials if any sign of compromise; enable authentication on all AI/MCP endpoints
- **Reference:** <https://thehackernews.com/2026/07/new-nadmesh-botnet-hunts-exposed-ai.html>
